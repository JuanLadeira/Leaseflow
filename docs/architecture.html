2 · Backend · decidido

Apps com cinco camadas

Cada app tem as mesmas cinco camadas e a dependência só anda num sentido. Só o repository toca o ORM, então o service fica testável com um repository falso.

routers.pyHTTP: path, auth, status code. Recebe e devolve schemas.
→
services.pyRegra de negócio: mudar status do lead, agendar visita sem conflito.
→
repositories.pyAcesso a dados async: aget, filtros, select_related.
→
models.pyTabelas e relações do Django ORM.
schemas.pyContrato de entrada e saída (Ninja Schema / Pydantic). Usado pelo router e pelo service; nunca expõe o model direto.
backend/apps/leads/
├── models.py        # Lead(unit FK, status, source)
├── schemas.py       # LeadOut, LeadFilters, LeadStatusIn
├── repositories.py  # LeadRepository.list(filters, page)
├── services.py      # LeadService.set_status(id, status)
├── routers.py       # router = Router(tags=["leads"])
├── admin.py
├── apps.py
├── migrations/
└── tests/
    ├── test_services.py   # repository mockado
    └── test_routers.py    # Ninja TestAsyncClient

Regras que valem a pena escrever no README

  • Um app só importa o services de outro app, nunca o repository ou o model. Ex.: visits chama LeadService.get().
  • assistant lê o lead via LeadService e não tem tabela própria no MVP.
  • core/ guarda o BaseRepository genérico e o schema de paginação, para não repetir em cada app.
  • Erros de domínio são exceções em services; um handler em config/api.py converte para 404/409.
3 · Frontend · decidido

Quatro decisões para fechar

Cada bloco tem três caminhos. O critério é o mesmo: o que fica pronto até terça e o que rende boa conversa numa entrevista de React.

A. Como agrupar as pastas

A decisão que define todas as outras.

Por camada
src/
├── components/
├── hooks/
├── pages/
├── services/
└── store/
  • Todo tutorial usa, zero atrito
  • O lead fica espalhado em 5 pastas
  • Não conversa com o backend, que é por app
Por feature + shared/recomendado
src/
├── app/
├── features/
│   └── leads/
│       ├── leadsApi.ts
│       ├── components/
│       ├── hooks/
│       ├── pages/
│       └── index.ts
└── shared/ api ui hooks lib
  • Espelha os apps do Django: leads ↔ leads
  • Casa com injectEndpoints do RTK Query
  • Precisa de uma regra para o que vai em shared/
Feature-Sliced Design
src/
├── app/
├── pages/
├── widgets/
├── features/
├── entities/
└── shared/
  • Regras de import formais e lintáveis
  • 6 camadas para 6 telas é cerimônia
  • "Isso é entity ou feature?" toma tempo

Recomendo: por feature. Regra de import: uma feature só importa o index.ts de outra, e shared/ nunca importa de features/. Dá para travar isso com eslint-plugin-import (no-restricted-paths). Do scaffold atual, falta mover api/ auth/ theme/ hooks/ utils/ components/ da raiz de src/ para shared/.

B. Onde mora cada tipo de estado

Pergunta 4 e 6 do plano: Context vs Redux, server state vs client state.

Tudo no Redux
store/
├── authSlice.ts
├── leadsSlice.ts   thunks
├── uiSlice.ts      tema, modais
└── filtersSlice.ts
  • Um lugar só, DevTools vê tudo
  • Cache, loading e refetch escritos à mão
  • Não mostra Context, que a vaga pede
Cada estado no seu lugarrecomendado
servidor  RTK Query
sessão    AuthContext (split)
tema      ThemeContext
filtros   URL (useSearchParams)
form      React Hook Form
otimista  useOptimistic
  • Cada ferramenta faz o que faz melhor
  • Resposta pronta para "Context or Redux?"
  • Filtros na URL: link compartilhável e voltar funciona
  • Mais conceitos para explicar no README
Sem Redux
servidor  TanStack Query
resto     Context / Zustand
  • Stack mais leve e muito usada
  • A vaga pede Redux Toolkit ou MobX
  • Troca o que o scaffold já tem

Recomendo: a do meio, que é quase o que o scaffold já faz. Slices do Redux ficam só se surgir estado de cliente compartilhado de verdade (ex.: rascunho da resposta da IA entre telas). Isso vira uma tabela de duas colunas no README e uma resposta de 30 segundos na entrevista.

C. Onde ficam as rotas

Como as features entram no React Router e onde entra o code splitting.

Um router.tsx central
app/router.tsx
importa todas as pages
e monta a árvore
  • Mapa de rotas legível num arquivo
  • Conhece o interior de cada feature
  • Lazy load espalhado pelo arquivo
Feature exporta suas rotasrecomendado
features/leads/routes.tsx
export const leadsRoutes
  = [{ path, lazy }]
app/router.tsx
  ...leadsRoutes,
  ...visitsRoutes
  • Cada feature vira um chunk com lazy
  • router.tsx continua curto e só compõe
  • Precisa olhar dois arquivos para ver uma rota
File-based (TanStack Router)
src/routes/
├── __root.tsx
├── leads.index.tsx
└── leads.$id.tsx
  • Rotas tipadas de ponta a ponta
  • Mais uma ferramenta para aprender em 3 dias
  • Briga com a organização por feature

Recomendo: cada feature exporta suas rotas com lazy e o app/router.tsx só junta tudo sob o layout com RequireAuth. O dashboard com o gráfico é o melhor exemplo de chunk separado para mostrar no Profiler e no relatório do build.

D. Estilo e testes

Onde fica o CSS e onde ficam os testes.

Tailwind + __tests__/
LeadRow.tsx  className="flex …"
__tests__/LeadRow.test.tsx
  • Rápido de montar tela
  • Esconde o CSS3 (Grid, media query) que a vaga pede
  • Teste longe do componente
CSS Modules, teste coladorecomendado
components/LeadRow/
├── LeadRow.tsx
├── LeadRow.module.css
└── LeadRow.test.tsx
shared/theme/tokens.css vars
  • Mostra Grid, Flexbox e mobile-first escritos à mão
  • Abre a pasta, vê tudo do componente
  • Um pouco mais lento que Tailwind
Lib de UI (MUI, Mantine)

  • Tabela e calendário prontos
  • Não prova acessibilidade nem CSS próprio

Recomendo: CSS Modules com tokens em variáveis CSS (o tema claro/escuro do ThemeContext troca as vars) e teste ao lado do componente. Testes de fluxo, com MSW, ficam em features/leads/__tests__/.

4 · Ambientes · decidido

O que cada compose sobe

Um Dockerfile por serviço com stages nomeados; cada arquivo de ambiente escolhe o stage com build.target.

Ambientedbbackendfrontendnginx
dev.yml postgres:17volume nomeado, porta 5432 target devuvicorn --reload, código montado target devvite --host :5173, proxy /api → backend —
test.yml postgres:17tmpfs, sem volume target testruff + pytest target testeslint + tsc + vitest run —
prod.yml postgres:17ou banco gerenciado no deploy target prodgunicorn -k uvicorn_worker target buildsó gera dist/, copiado para o nginx nginx:alpineserve SPA, proxy /api, SSE sem buffer

Com os yml dentro de compose/, o contexto de build é .. e o .dockerignore precisa ficar na raiz do repo. No nginx, a rota do assistente precisa de proxy_buffering off, senão o streaming chega todo de uma vez.
